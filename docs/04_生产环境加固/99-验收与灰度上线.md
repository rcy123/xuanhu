## 1. 整体验收门禁

每个阶段独立验收，但所有阶段需通过后才能整体灰度上线。验收分两层：

1. **阶段内自验收**：各阶段文档末尾的验收清单逐条勾选（自动化测试 + 人工 checklist）。
2. **整体回归验收**：四阶段全完成后，跑一次完整临床工作流端到端，确认医师从登录→问诊→辨证→开方→安全审核→确认→病历无回归。

## 3. 灰度上线方案

### 3.1 双密钥灰度（JWT）

阶段 1 引入 `JWT_SIGNING_KEY` 时，支持新旧双密钥交接：

- 新增 `JWT_SIGNING_KEY_PREVIOUS`（可选）。
- `get_current_doctor` 校验时：先用 `JWT_SIGNING_KEY` 验签；失败再用 `PREVIOUS` 验签。
- 颁发永远只用新 key。
- 灰度期先切颁发密钥，等所有老 token 过期（≤8h），再移除 `PREVIOUS`。

这样上线零登出。

### 3.2 开关灰度

各阶段引入的环境开关统一成"三态"语义：

| 值 | 含义 |
|---|---|
| `off` | 该阶段加固完全不生效（回退态） |
| `audit` | 加固逻辑生效但仅记审计、不阻断（观察期） |
| `on` | 加固逻辑生效且阻断（正式态） |

涉及开关：

- `XUANHU_AUTH_ENABLED` = off / audit / on（阶段 1）
- `XUANHU_ACCESS_ENABLED` = off / audit / on（阶段 2）
- `XUANHU_PROD_SECRET_GUARD` = off / on（阶段 3，无 audit 态——要么校验要么不校验）
- `XUANHU_RATELIMIT_ENABLED` = off / on（阶段 4）

灰度路径：

```
Day 0  : 各开关=off 部署 → 验证无回归
Day 1  : AUTH=audit → 观察 24h 审计日志，确认无合法流量被误判
Day 2  : AUTH=on → 正式生效；ACCESS=audit
Day 3  : ACCESS=on；SECRET_GUARD=on；RATELIMIT=on
Day 4+: 移除 off/audit 分支代码（生产稳定后）
```

> 移除 off/audit 分支是关键——避免这些开关成为永久后门。移除时机由安全评审人把关。

### 3.3 红蓝对抗验证

灰度 `on` 稳定一周后，安排一次蓝队演练，模拟：

- 无 token 访问业务接口
- 伪造医师身份访问他人会话
- 在日志中搜索 PHI
- 试图调用 `/docs`
- 暴力登录

验证全部被拦截且审计留痕。该演练结果归档为上线最终批准材料。

## 4. 上线后持续安全基线

上线后转为持续安全运维，不属于本组文档，但记录在此作为衔接：

- **依赖漏洞扫描**：每次 `uv lock` / `npm install` 后跑 `pip-audit` / `npm audit`，CI 阻断高危。
- **密钥定期轮换**：`MODEL_GATEWAY_API_KEY` 每 90 天轮换一次（自动化提醒）。
- **审计审查**：每周 review `access.denied` / `config.drift` 事件集中度。
- **红蓝演练**：每季度一次。
