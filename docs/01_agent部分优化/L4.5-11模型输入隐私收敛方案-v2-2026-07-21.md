### 1.3 关键发现

**发现 1：Intake USER 层原文缺口**

`build_intake_context()` 将 `current_messages` JSON 序列化后直接放入 USER 层：

```python
# app/agents/intake_extraction.py:119
user=json.dumps(current_messages, ensure_ascii=False, separators=(",", ":")),
```

该 USER 层**不经过** `ContextBuilder.project()` 的 Mapping/string 投影，因此 `_redact_free_text()` 的裸号码模式匹配**不会**应用于 Intake 的原始患者消息。

**发现 2：ContextBuilder 投影仅覆盖 CONTEXT 层**

```python
# app/agent_runtime/context.py:158-168
def build(self, *, system: str, developer: str, context: Mapping[str, Any] | str = "", user: str = "") -> ContextPacket:
    projected = self.project(context) if isinstance(context, Mapping) else ...
    # ...
    messages = tuple(PromptMessage(role=role, content=text) for role, text in (
        (PromptLayer.SYSTEM, system),
        (PromptLayer.DEVELOPER, developer),
        (PromptLayer.CONTEXT, context_text),
        (PromptLayer.USER, user),  # <-- user 直接传入，不经过投影
    ) if text)
```

**发现 3：当前调用链无最终 Gateway 门禁**

```
ConsultMessage.content
  -> _build_intake_input()
  -> IntakeExtractionInput.current_messages
  -> build_intake_context()  # USER 层 = JSON(current_messages)
  -> ContextPacket.messages
  -> execute_intake_extraction()

```

## 4. 模型输入独立投影策略

### 4.1 策略比较

| 策略 | 描述 | 优点 | 缺点 | 选定 |
|---|---|---|---|---|
| **A：USER 层投影增强** | 在 `ContextBuilder.build()` 中对 USER 层也应用 `_redact_free_text()` | 改动最小，复用现有机制 | USER 层是 JSON 序列化后的混合文本，投影结果不可用于 grounding | 不推荐 |
| **B：Intake 入口投影** | 在 `build_intake_context()` 之前，对 `current_messages` 逐条应用投影 | 投影发生在数据最早的可干预点； grounding 可基于原文验证 | 需要修改 Intake 输入构建流程 | **推荐** |
| **C：Gateway 最终门禁** | 在 `AgentRuntime._call_gateway()` 或 `ModelGatewayClient` 中对最终请求做扫描 | 最终兜底，fail-closed | 无法用于 grounding（模型已看到原文） | 作为补充，不作为唯一防线 |

### 4.2 推荐策略：B + C（入口投影 + Gateway 兜底）

```
患者消息
   │
   ▼
[层 1: Intake 入口投影]  ← 新
   │
   │  对 current_messages 逐条应用 _redact_free_text()
   │  保留原始消息用于 grounding（不修改持久化消息）
   │  投影结果写入 ContextPacket.messages[USER]
   │
   ▼
[层 2: ContextBuilder 投影]  ← 现有（已覆盖 CONTEXT 层）
   │
   ▼
[层 3: Gateway 最终门禁]  ← 新
   │
   │  在 _call_gateway() 中对最终 messages 做极简扫描
   │  命中即 fail-closed，零 Gateway 请求
   │
   ▼
模型 Gateway
```

### 4.3 关键设计决策

**决策 1：投影是派生数据，不成为 Domain 或持久化原文的新事实源**

- 投影仅作用于 `ContextPacket.messages`（模型输入）
- 不修改 `ConsultMessage.content`、`IntakeMessage.content` 或任何持久化数据
- 投影失败不影响原始消息

**决策 2：临床数字保护**

- 采用"字段名 + 数值范围 + 单位"三重白名单
- 仅当字段名命中白名单 AND 数值在范围内 AND 单位匹配时保留数字
- 其余连续数字 token 一律脱敏

**决策 3：等长替换**

- 使用等长占位符（如 `[REDACTED:13]` 表示 13 位数字被替换）
- 保持 `EvidenceSpan` 的 offset 不变性（详见第 5 节）

## 5. EvidenceSpan 与 Grounding 机制

### 5.1 策略比较

| 策略 | 等长替换 | Offset Map |
|---|---|---|
| **描述** | 用等长占位符替换敏感文本，保持字符位置不变 | 维护投影-to-原文的 offset 映射表 |
| **模型可见** | 占位符（如 `[REDACTED:13]`） | 占位符或假名 |
| **Grounding 验证** | 直接用原始消息验证（offset 不变） | 通过映射表将模型返回的 offset 映射回原文 |
| **NFKC 处理** | 投影前对原文做 NFKC，验证时也做 NFKC | 同上，映射表基于 NFKC 后的文本 |
| **实现复杂度** | 低 | 高（需维护每条消息的映射表） |
| **选定** | ✅ **推荐** | 备选 |

### 5.2 推荐策略：等长替换

**理由：**

1. **Grounding 验证可直接使用原文**：`EvidenceSpan.start_char` 和 `end_char` 在原文和投影后文本中指向同一位置
2. **无需额外映射表**：减少复杂度和出错面
3. **与现有 grounding 验证器兼容**：`intake_grounding.py` 的 `_verified_message()` 可直接使用原文验证

**等长替换规则：**

| 原始文本 | 替换后 | 长度保持 |
|---|---|---|
| `13800138000`（11 位手机号） | `[REDACTED:11]` | ✅ 11 字符 |
| `110101199001011234`（18 位身份证号） | `[REDACTED:18]` | ✅ 18 字符 |
| `张三`（姓名） | `[REDACTED:2]` | ✅ 2 字符 |

**Grounding 验证流程：**

```
模型返回 EvidenceSpan
       │
       ▼
┌─────────────────────────────────────┐
│ 1. 获取 source_message_id            │
│ 2. 从原始消息获取 content（未投影）    │
│ 3. 验证 start_char/end_char 范围      │
│ 4. 验证 message[start:end] == quote   │
│ 5. 通过 → 返回验证结果               │
└─────────────────────────────────────┘
```

### 5.3 防止假名/占位符反向写入患者事实

| 机制 | 说明 |
|---|---|
| **投影仅在模型输入层** | 模型看到的占位符不会进入 Domain State |
| **Grounding 验证使用原文** | 验证器比较的是原文 quote，不是投影后的占位符 |
| **输出 canonicalization** | `canonicalize_intake_output()` 重建标准 DTO，拒绝未声明字段 |
| **Verifier 链** | `INTAKE_VERIFIER_CHAIN` 包含 grounding、authority_boundary 等检查 |

## 6. 最终不可绕过门禁

### 6.1 门禁位置

```
AgentRuntime._call_gateway()
   │
   ▼
┌─────────────────────────────────────────────────────────────┐
│ 最终隐私门禁（新）                                           │
│                                                             │
│  输入：messages（最终发送给 Gateway 的列表）                 │
│  行为：                                                      │
│    1. 遍历每条消息的 content                                  │
│    2. 对 content 做极简裸串扫描（仅原始 ASCII 数字）         │
│    3. 若发现裸手机号/身份证号 → 命中门禁                     │
│    4. 命中时抛出固定失败码，不调用 Gateway                    │
│                                                             │
│  注意：                                                      │
│    - 扫描的是最终序列化请求（JSON 已转义后的字符串）           │
│    - 不处理全角/转义/跨分片（由入口投影层负责）               │
│    - 作为 fail-closed 兜底，不是主要防线                     │
└─────────────────────────────────────────────────────────────┘
   │
   ▼
ModelGatewayClient.chat_structured_observed()
```

### 6.2 门禁设计

| 属性 | 值 |
|---|---|
| **位置** | `AgentRuntime._call_gateway()` 中，实际 Gateway 调用之前 |
| **覆盖范围** | 所有 Intake 模型请求（`execute_intake_extraction` → `runtime.run` → `_call_gateway`） |
| **Fallback/Retry** | 是。structured-output fallback 或重试仍经过同一门禁（在 `_call_gateway` 中） |
| **扫描对象** | 最终序列化请求（`messages` 列表中的 `content` 字符串） |
| **命中失败码** | `RuntimeErrorCode.MODEL_INPUT_PRIVACY_VIOLATION`（新） |
| **审计内容** | 记录失败码、attempt、trace_id；**不记录**命中的原始值 |
| **零请求保证** | 门禁命中时直接抛出异常，**不调用** `self.gateway.chat_structured` 或 `chat_structured_observed` |

### 6.3 失败码定义

```python
class RuntimeErrorCode(StrEnum):
    # ... 现有码 ...
    MODEL_INPUT_PRIVACY_VIOLATION = "MODEL_INPUT_PRIVACY_VIOLATION"
    """最终 Gateway 请求包含未授权 PII；已 fail-closed，零 Gateway 请求。"""
```

### 6.4 测试证明 Gateway 零请求

| 测试用例 | 期望行为 |
|---|---|
| 门禁命中时 Gateway 调用次数为 0 | Mock gateway 的 `chat_structured` 未被调用 |
| 门禁未命中时正常通过 | Mock gateway 的 `chat_structured` 被调用一次 |
| 失败码固定且不包含原始值 | 异常码为 `MODEL_INPUT_PRIVACY_VIOLATION`，异常消息不含 PII |

### 6.5 其他 Agent 复用

| Agent | 是否复用该门禁 | 说明 |
|---|---|---|
| IntakeExtraction | ✅ 是 | 当前任务目标 |
| 其他 Agent（Syndrome/Sufficiency 等） | ❌ 否（当前任务） | 若需复用，在后续任务中明确 |

### 8.1 风险矩阵

| 风险 | 级别 | Owner | 缓解措施 | 触发条件 |
|---|---|---|---|---|

| R5：与现有 Agent 冲突 | P2 | 开发 | 仅修改 Intake 路径；其他 Agent 不变 | 非 Intake Agent 测试失败 |

### 8.2 停止条件

| 条件 | 行为 |
|---|---|
