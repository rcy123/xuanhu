## 3. 有限威胁模型

### 3.1 保护对象（有限集）

| 威胁族 | 描述 | 当前代码中的存在形式 |
|---|---|---|
| **T1：结构化身份键** | `_PII_KEYS` 中的 `name`、`phone`、`id_card` 等明确键 | 可能出现在 CONTEXT Mapping；已有 `ContextBuilder.project()` 假名化/脱敏。当前 `IntakeMessage` 本身没有这些字段 |
| **T2：连续手机号** | 中国大陆 11 位手机号（`1[3-9]\d{9}`） | 同上，以裸串形式存在于原文中 |
| **T3：连续身份证号** | 中国大陆 18 位身份证号（`\d{17}[\dXx]`） | 同上，以裸串形式存在于原文中 |

**注**：当前 Intake 模型输入 schema（`IntakeMessage`）只含 `message_id` 和 `content`，不含结构化姓名字段。自由文本中的姓名识别不在当前有限威胁模型覆盖范围内，列为残余风险（见 3.5 节）。

### 3.2 支持集合与有限 grammar

匹配器只接收下列字符类，不做“其余连续数字全部脱敏”：

- `D`：ASCII `0-9` 或全角 `０-９`；全角字符逐字符映射为一个 ASCII digit；
- `X`：ASCII `X/x` 或全角 `Ｘ/ｘ`，逐字符映射为一个 ASCII `X/x`；
- `S`：且仅限一个 ASCII 空格（U+0020）、连字符 `-`（U+002D）或点号 `.`（U+002E）；
- `B`：两条相邻有序 message content 之间的虚拟零宽边界，不对应原文字符；
- 其他字符均为硬边界，终止当前候选。

有限 grammar：

| 标识类型 | 接受形式 | 明确不接受 |
|---|---|---|
| 手机号 | `1[3-9]D{9}`；或 `1[3-9]D S D{4} S D{4}`，两个 `S` 必须是同一种字符 | 任意分组、多个空格、下划线、斜杠、任意标点 |
| 身份证号 | `D{17}[DXx]`，不带分隔符 | 带分隔符、15 位旧号码、任意其他证件号 |

`B` 可插入上述 grammar 的任意两个字符 token 之间，只用于检测同一有序输入中的跨 message 重组。扫描输入不是字符串粗暴拼接，而是 `(normalized_token, message_index, raw_char_index)` 序列；`B` 保留 message 边界，命中坐标可以确定性映射回每条原始 message。入口投影按这些坐标分别等长遮罩；最终门禁只拒绝，不改写，因此不需要产生新 offset。

NFKC 仅用于复核单个已允许字符的等价值。实现不得先对整段文本做 NFKC；任何规范化后不是“一原始字符 → 一 ASCII token”的字符都按硬边界处理并列入非目标。

## 4. 模型输入独立投影策略

### 4.1 策略比较

| 策略 | 描述 | 优点 | 缺点 | 选定 |
|---|---|---|---|---|
| **A：USER 层投影增强** | 在 `ContextBuilder.build()` 中对 USER 层也应用 `_redact_free_text()` | 改动最小，复用现有机制 | USER 层是 JSON 序列化后的混合文本，投影结果不可用于 grounding | 不推荐 |
| **B：Intake 入口投影** | 在 `build_intake_context()` 之前，对 `current_messages` 逐条应用投影 | 投影发生在数据最早的可干预点； grounding 可基于原文验证 | 需要修改 Intake 输入构建流程 | **推荐** |
| **C：Runtime 发送前门禁** | 在 `AgentRuntime._call_gateway()` 调用 Gateway 方法之前，对已构造 messages 做扫描 | Intake-only、命中时 Gateway 方法零调用 | 不修改内容，只能拒绝 | 作为补充，不作为唯一防线 |

### 4.2 推荐策略：B + C（入口投影 + Runtime 发送前兜底）

```
患者消息
   │
   ▼
[层 1: Intake 入口投影]  ← 新
   │
   │  对 current_messages 构造带原始坐标的有限 token 流
   │  单条及跨 message 命中均映射回原文并逐字符等长遮罩
   │  保留原始消息用于 grounding（不修改持久化消息）
   │  投影结果写入 ContextPacket.messages[USER]
   │
   ▼
[层 2: ContextBuilder 投影]  ← 现有（已覆盖 CONTEXT 层）
   │
   ▼
[层 3: Runtime 发送前门禁]  ← 新
   │
   │  在 _call_gateway() 调用 Gateway 方法前扫描最终 messages
   │  命中即 fail-closed，零 Gateway 请求
   │
   ▼
模型 Gateway
```

### 4.3 关键设计决策

**决策 1：投影是派生数据，不成为 Domain 或持久化原文的新事实源**

- 投影仅作用于 `ContextPacket.messages`（模型输入）
- 不修改 `ConsultMessage.content`、`IntakeMessage.content` 或任何持久化数据
- 投影失败不影响原始消息

**决策 2：有限身份 grammar，临床数字保持不变**

- 只匹配 3.2 节列出的手机号/身份证号 grammar；不采用宽泛连续数字规则；
- 不引入临床字段名、数值范围或单位白名单；
- 体温、血压、心率、血糖、日期和剂量是必须保持不变的负向不变量；
- 若未来要扩大数字识别范围，必须重新进行临床 owner 与隐私/法律外部审定，不能在实现任务内追加例外。

**决策 3：等长替换**

- 使用等长占位符（`█` 重复 N 次，N = 原文长度）
- 保持 `EvidenceSpan` 的 offset 不变性（详见第 5 节）
- **禁止**使用 `[REDACTED:N]` 等标签形式（经复验：`[REDACTED:11]` 为 13 字符，不等长）

## 5. EvidenceSpan 与 Grounding 机制

### 5.1 策略比较

| 策略 | 等长替换 | Offset Map |
|---|---|---|
| **描述** | 用等长占位符替换敏感文本，保持字符位置不变 | 维护投影-to-原文的 offset 映射表 |
| **模型可见** | 占位符（`█` 重复 N 次） | 占位符或假名 |
| **Grounding 验证** | 直接用原始消息验证（offset 不变） | 通过映射表将模型返回的 offset 映射回原文 |
| **NFKC 处理** | **替换在原始文本上进行**；NFKC 仅用于匹配辅助，不参与替换 | 映射表基于原始文本 |
| **实现复杂度** | 低 | 高（需维护每条消息的映射表） |
| **选定** | ✅ **推荐** | 备选 |

### 5.2 推荐策略：等长替换

**理由：**

1. **Grounding 验证可直接使用原文**：`EvidenceSpan.start_char` 和 `end_char` 在原文和投影后文本中指向同一位置
2. **无需持久化 projection-to-source offset map**：scanner 只在本次调用内保存原始字符坐标并等长回写
3. **与现有 grounding 验证器兼容**：`intake_grounding.py` 的 `_verified_message()` 可直接使用原文验证

**关键不变量：**
- 替换在**原始文本**上进行，不经过 NFKC 规范化
- token 流中的每个非 `B` 命中项都携带 `(message_index, raw_char_index)`；将该原始坐标上的字符替换为一个 `█`
- `B` 是零宽边界，不产生替换；跨 message 命中分别回写各 message，保持每条 message 的总字符数不变
- 验证器使用**原始消息**（未投影）验证 quote/offset

**等长替换规则：**

| 原始文本 | 替换后 | 长度保持 |
|---|---|---|
| `13800138000`（11 位手机号） | `███████████`（11 个 `█`） | ✅ 11 字符 |
| `110101199001011234`（18 位身份证号） | `██████████████████`（18 个 `█`） | ✅ 18 字符 |

**复验命令：**

```powershell
$env:PYTHONUTF8='1'
uv run python -c "print(len('█' * 11), len('█' * 18))"
# 输出: 11 18
```

**NFKC 行为声明：**

- `█`（U+2588）经 NFKC 规范化后仍为 `█`，长度不变
- 匹配 shadow 只为 ASCII digit/X 和明确列出的全角 digit/X 逐字符生成；每个 shadow token 保存唯一原始坐标
- 全角数字（如 `１３８`）在 shadow 中匹配为 `138`；匹配成功后，用坐标回到原始文本，将三个全角字符分别替换为三个 `█`
- 任一字符若规范化为零个或多个 token，或不在允许字符类中，就作为硬边界；不尝试跨该字符匹配
- **禁止先 NFKC 再替换**：NFKC 可能扩展字符（如 `㍑` → `リットル`，1 字符 → 3 字符），导致 offset 漂移

**JSON 与 EvidenceSpan 坐标声明：**

- 先在每条 `IntakeMessage.content` 原始副本上等长遮罩，再 JSON 序列化；
- prompt 契约中的 `EvidenceSpan.start_char/end_char` 始终表示 `source_message_id` 对应的原始 `content` 坐标，不是整个 JSON 字符串中的绝对坐标；
- 非 PII 临床片段在投影前后坐标相同，可继续按原文 quote/offset 校验；任何跨入遮罩区的 quote 会与原文不一致并由 grounding fail-closed 拒绝。

**Grounding 验证流程：**

```
模型返回 EvidenceSpan
       │
       ▼
┌─────────────────────────────────────┐
│ 1. 获取 source_message_id            │
│ 2. 从原始消息获取 content（未投影）    │
│ 3. 验证 start_char/end_char 范围      │
│ 4. 验证 message[start:end] == quote   │
│ 5. 通过 → 返回验证结果               │
└─────────────────────────────────────┘
```

### 5.3 防止假名/占位符反向写入患者事实

| 机制 | 说明 |
|---|---|
| **投影仅在模型输入层** | 模型看到的占位符不会进入 Domain State |
| **Grounding 验证使用原文** | 验证器比较的是原文 quote，不是投影后的占位符 |
| **输出 canonicalization** | `canonicalize_intake_output()` 重建标准 DTO，拒绝未声明字段 |
| **Verifier 链** | `INTAKE_VERIFIER_CHAIN` 包含 grounding、authority_boundary 等检查 |

## 6. 最终不可绕过门禁

### 6.1 重新核对后的真实请求边界

**方案选择：Intake-only Runtime 发送前门禁。**

```text
AgentRuntime._call_gateway(agent_spec, run_spec, messages)
   │
   ├─ agent_spec.name != INTAKE_AGENT_NAME ──> 维持原行为（非本任务范围）
   │
   └─ agent_spec.name == INTAKE_AGENT_NAME
         │
         ├─ 对最终 Runtime messages 构造有限 token/坐标流
         ├─ 命中支持集合 ──> RuntimeErrorBase(MODEL_INPUT_PRIVACY_VIOLATION)
         │                    Gateway 方法调用次数 = 0
         └─ 未命中 ─────────> chat_structured_observed(..., max_requests=1)
                                   │
                                   └─ _chat_structured_impl() 构造 payload 并发送
```

当前代码事实决定了这一边界能够覆盖目标 Intake 请求：

| 代码事实 | 结论 |
|---|---|
| `_call_gateway()` 在调用真实 Gateway 方法前持有完整 `messages` 与 `agent_spec.name` | 可在共享 Runtime 内精确限制为 Intake-only，命中时 Gateway 方法零调用 |
| `_call_gateway()` 对支持该参数的真实方法传 `max_requests=1` | `_request_with_retry()` 的 HTTP 尝试上限为 1；结构化解析循环上限为 1 |
| `_chat_structured_impl()` 在 `max_requests is not None` 时于 JSON fallback 前 `break` | AgentRuntime Intake 路径**不会进入** `_chat_structured_json_fallback()` |
| 主 payload 的 `messages` 直接引用 Runtime 传入的 `messages` | 发送的患者来源文本与门禁扫描对象相同；tools/schema/trace 元数据由代码生成，不含患者消息 |
| Legacy Agent 直接调用 `ModelGatewayClient`，不经过 `AgentRuntime` | Legacy 和直接 Gateway 调用明确不在本任务覆盖范围内，不得宣称已保护 |

R1 中“每次 retry 重新构造 payload”“fallback 会经过 `_chat_structured_impl()` 入口门禁”均不符合代码：传输 retry 重用同一个 payload；JSON fallback 在独立函数内构造并直接请求。由于目标 Runtime 路径固定 `max_requests=1`，两条扩张路径在发送前已被关闭，因此无需把 AgentRuntime 的失败码反向依赖到 `app/core/gateway.py`。

### 6.2 门禁扫描输入与消息边界

门禁复用 3.2 节的有限 scanner，但行为是“检测并拒绝”，不修改消息：

1. 按最终 `messages` 的既有顺序读取每个字符串 `content`；
2. 每个字符生成 `(token, message_index, raw_char_index)`，相邻 messages 间插入 `B`；
3. 对单 message 与跨 message token 流匹配手机号/身份证号 grammar；其他字段、role、message dict 的序列化结果不加入扫描输入；
4. 命中只返回布尔值/类型枚举，禁止把原文、命中片段、坐标或 message content写入异常、日志与 recorder；
5. Intake message 缺少字符串 `content`、token 化失败或映射异常，一律按同一固定失败码 fail-closed。

入口投影还会在 JSON 序列化前对 `IntakeExtractionInput.current_messages[*].content` 使用同一坐标 scanner，因此原始 Intake 消息被跨 message 拆分时也能映射回各条原文遮罩；Runtime 门禁负责捕获单层最终 messages 中的残留或入口绕过。两层边界不可互相替代。

### 6.3 失败码与异常归属

```python
class RuntimeErrorCode(StrEnum):
    # ... 现有码 ...
    MODEL_INPUT_PRIVACY_VIOLATION = "MODEL_INPUT_PRIVACY_VIOLATION"
```

- 异常类型仍为 `RuntimeErrorBase`，定义和归一化均留在 `app/agent_runtime`；
- `app/core/gateway.py` 不导入 `app.agent_runtime.specs`，避免 core → agent_runtime 的反向依赖；
- `execute_intake_extraction()` 已捕获 `RuntimeErrorBase` 并只返回固定 `failure_code`。

### 6.4 零请求与覆盖证明

| 测试用例 | 期望行为 |
|---|---|
| 不安全 Intake messages 直接送入 `AgentRuntime.run()` | Fake Gateway 的 `chat_structured_observed` 与 `chat_structured` 合计调用 0 次 |
| 安全 Intake messages | Gateway 方法调用 1 次，并收到 `max_requests=1` |
| 分隔/全角/跨最终 message 命中 | 全部固定失败码、Gateway 方法 0 次 |
| 扫描器内部异常 | fail-closed 为同一失败码、Gateway 方法 0 次 |
| 失败输出与 recorder | 只含失败码/attempt/trace_id；不含原始值、命中片段或坐标 |
| 非 Intake AgentSpec 使用同一 Runtime | 本门禁不触发，现有行为与回归测试保持不变 |

### 6.5 覆盖边界

| 路径 | 本方案是否覆盖 | 说明 |
|---|---|---|
| `execute_intake_extraction()` → `AgentRuntime` → Gateway | ✅ | 当前目标路径；入口投影 + Runtime 门禁 |
| 其他 AgentRuntime Agent | ❌ | 显式按 `INTAKE_AGENT_NAME` 限定；后续另行立项 |
| Legacy/BaseAgent 直接 Gateway 调用 | ❌ | 不经过 AgentRuntime；不得以本任务关闭其隐私风险 |
| 直接手工调用 `ModelGatewayClient` 且伪造 Intake 名称 | ❌ | 当前无生产调用；属于 Gateway 级通用策略的后续范围 |
