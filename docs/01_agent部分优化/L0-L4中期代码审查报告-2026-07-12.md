## 1. 执行结论

### 1.1 总结

L0–L4 **不是空壳实现**。仓库已经形成了较完整的双运行时迁移框架、LangGraph 主图、PostgreSQL checkpointer、强类型 Harness、Domain Repository、Intake 子图和 Reasoning 子图；L3-1～L4-3 的 299 条纯单元/边界测试本次全部通过，说明强类型契约、确定性策略和草案一致性边界具有较好的代码基础。

但进度表中的“L0–L4 均为 100% 已完成”与实际可交付状态不一致。当前存在两个必须阻止 LangGraph 默认启用或临床试用的 P0 问题：

1. `triage_precheck` 节点实际是空操作，红旗阻断完全依赖模型主动输出 `red_flag_candidates`；模型漏报时，确定性 TriagePolicy 会把“无候选”视为通过。
2. 测试默认连接通用 `DB_URL`，并执行迁移降级和 `TRUNCATE`；无测试库名称保护，且部分破坏性用例未标记为 integration。默认/并行门禁可能清空开发甚至误配的非测试数据库。

此外，初始主诉和患者安全信息没有进入新版 Domain State、公开幂等头没有被后端消费、LangGraph 恢复 API 仍走 Legacy、Outbox 无发布器、会话详情不投影 L3/L4 结果、前端无法创建/推进新版会话等问题，说明 L3/L4 目前属于“核心算法和子图边界已实现，但产品闭环与生产边界未完成”。

## 2. 已确认的优势

### 2.1 架构方向基本正确

- Domain State 与 Graph State 已实际分离。Graph State 主要保存 session/run/command、gate 和 artifact reference，临床事实保存在 PostgreSQL 领域表。
- LangGraph 主图已经将 `message` 接入 IntakeSubgraph、`advance` 接入 ReasoningSubgraph；review/recover 仍保留占位，与当前阶段边界一致。见 `app/agent_runtime/graph.py:89-149`。
- PostgreSQL checkpointer 对 `thread_id={graph_version}:{session_id}` 做不可绕过的写入校验，资源通过 context manager 关闭。见 `app/agent_runtime/checkpoint.py:61-128,131-180`。
- `GraphRunner` 有总超时、取消传播和固定错误码脱敏边界。见 `app/agent_runtime/runner.py:109-143`。

### 2.2 Harness 和权威数据边界较扎实

- AgentRuntime 将模型单元限制为无状态执行，不直接写 DB、路由或批准；AgentSpec/RunSpec/RunArtifact 均有强类型契约。
- ContextBuilder 采用白名单、分层消息、身份字段过滤和 token 预算。
- Verifier/Reducer/Repository 使用 schema、来源、stage、state version、幂等键和乐观并发控制，避免模型结果直接覆盖权威状态。
- Artifact revision 具备单 current、父 revision 约束和 payload digest；Formula 可按 base + modifications 确定性重建。
- L4 明确 `model_knowledge_only`、置信度上限、`review_required=true`，没有伪造 RAG citation。

### 2.3 测试对对抗性输入覆盖较多

- L3/L4 单元测试覆盖 `model_construct`、隐藏字段、复制对象、跨 session/run、篡改 provenance、身份字段变体和 Prompt injection 等绕过方式。
- 本次复跑 L1/L2 纯边界 126 条全部通过；L3-1～L4-3 纯边界 299 条全部通过。
- 前端 22 个测试文件、161 条测试通过；TypeScript 类型检查和生产构建通过。
- Ruff 全仓通过，`mypy app` 对 118 个应用源码文件通过。

这些优点说明当前代码值得继续演进，不建议推倒重来。整改重点应是把已经较强的“内部契约”接到真实输入、真实 API、真实恢复和真实用户界面上。

## 3. P0 阻断项

### P0-01：红旗预检是空节点，模型漏报可直接绕过 Triage Gate

**证据**

- 图中存在 `persist_message -> triage_precheck -> build_context -> extract` 的节点顺序：`app/agent_runtime/intake_subgraph.py:170-176`。
- 生产 `run_intake_triage_precheck_node()` 只写一条“步骤完成”元数据，没有读取消息、没有确定性规则、没有产生 gate：`app/services/langgraph_intake.py:754-766`。
- 真正的 TriagePolicy 输入仅来自模型输出的 `output.red_flag_candidates`：`app/services/langgraph_intake.py:1126-1130`。
- TriagePolicy 明确把空候选作为唯一的 `continue/passed` 路径：`app/agent_runtime/triage_policy.py:214-219`，对应测试 `tests/test_l3_2_triage_policy.py:70-81`。
- L3-5 红旗 E2E 使用会主动返回红旗候选的 fake gateway，并未覆盖“文本有红旗但模型漏报”：`tests/test_l3_5_intake_subgraph.py:308-341`。

**影响**

“胸痛、呼吸困难、意识改变、严重出血”等文本只要模型没有生成候选，就会被确定性规则视为无红旗。这与“红旗不能进入 Reasoning”的验收结论不等价，属于医疗安全硬门禁缺失。

**必须整改**

1. 在模型前实现只读、确定性、版本化的 raw-text red flag precheck，至少覆盖高召回关键词、数值阈值和否定/上下文处理。
2. 模型候选只能补充/升级，不能删除或降级确定性候选。
3. precheck 不确定时进入 `manual_review`，不能默认 continue。
4. 增加“模型返回空候选但原文包含每类高危红旗”的 API/E2E 回归。
5. 在试点前由临床人员审定规则集、同义词、否定词、时态和召回评估集。

### P0-02：测试可直接降级并清空通用开发数据库

**证据**

- `tests/conftest.py:13-21` 在测试收集时把 `DB_URL` 默认设为 `postgresql://.../xuanhu`，不是独立测试库。
- L2-1 fixture 无 integration 标记，直接 downgrade/upgrade，并在结束时把库留在 `20260710_0002`：`tests/test_l2_1_domain_schemas_and_migration.py:89-103`。
- L3-5 fixture 同样无 integration 标记，直接 downgrade/upgrade；每条用例 `TRUNCATE` 业务表：`tests/test_l3_5_intake_subgraph.py:225-258`。
- L2-5/L4-4 虽标记 integration，仍只读取通用 `DB_URL`，执行迁移和 `TRUNCATE`：`tests/test_l2_5_repository_outbox.py:49-74`、`tests/test_l4_4_reasoning_subgraph.py:77-108`。
- `pyproject.toml` 默认 `testpaths = ["tests"]`，默认执行不会自动排除 integration。

**本次复跑事实**

- 两个最初并行启动的全量 pytest 因共享数据库迁移/锁竞争长期不结束，已只终止本次确认的 pytest 父子进程。
- 顺序执行 `pytest -m "not integration"` 得到 `1198 passed / 1 failed / 13 errors / 289 deselected`；错误根因是 L2-1 把库留在 `0002` 后，L3-5 尝试从 `0002` downgrade 到 `0004`。
- 将 schema 恢复到 head 后，之前失败的 L4 checkpoint 用例独立复跑通过，说明该失败是迁移夹具污染，而非 L4 业务回归。
- 本次已执行 `alembic upgrade head`，当前 schema 为 `20260712_0007 (head)`。
- 当前只读行数检查结果为：`consult_sessions=1`，其余检查的消息、Observation、Artifact、Gate、GraphRun、Outbox、Review、Record 表均为 0。没有测试前基线，无法判断或恢复此前数据。

**影响**

- 开发数据丢失；误配时存在测试清理非测试库的风险。
- 测试结果依赖文件顺序和上一个 fixture 留下的迁移版本。
- 无法安全并行，CI worker 之间互相污染。
- “全量测试通过”的历史结论不可直接信任。

**必须整改**

1. 只允许 `TEST_DATABASE_URL`，禁止 destructive fixture 使用 `DB_URL`。
2. 启动前解析数据库名并要求显式 `_test` 后缀；同时要求环境哨兵，如 `XUANHU_ALLOW_DESTRUCTIVE_TESTS=1`。
3. 每个 worker 创建独立临时数据库/schema，测试后删除；不要共享开发库。
4. 所有真实 PG/Redis 用例统一标记 integration，默认单元门禁显式 `-m "not integration"`。
5. migration fixture 必须记录原 head 并在 `finally` 恢复，setup 失败也要恢复。
6. CI 中增加“数据库名保护负向测试”和 `pytest-xdist` 并行隔离验证。

## 4. P1 高优先级问题

### P1-01：创建会话时的主诉、年龄、性别和安全信息未进入新版 Domain State

`SessionService.create_session()` 只把 `patient_info` 和 `chief_complaint` 写入 `consult_sessions`：`app/services/session.py:76-91`。新版 Intake 模型输入只包含“本次提交消息 + 已有 Observation”，没有读取 session 的主诉或患者信息：`app/services/langgraph_intake.py:1463-1479`。

结果是：

- WebUI 创建会话时已填写的主诉，进入新版问诊后仍可能被再次询问。
- API 传入的年龄、性别、过敏、妊娠等不会成为 Completeness/Safety 的权威输入。
- 医师可能误以为创建页数据已参与后续安全判断。

应在会话创建事务中做版本化、可审计的 initial Domain seed：非身份类人口学事实写 Observation，过敏/妊娠/用药等写 SafetyProfile；需定义初始表单与后续消息冲突、更正和 retract 规则。姓名、门诊号等不得进入模型上下文。

### P1-02：公开 `X-Idempotency-Key` 被前端发送但后端完全忽略

- 前端通用客户端会发送 `X-Idempotency-Key`：`frontend/src/api/client.ts:89-97`。
- 创建会话明确生成该键：`frontend/src/hooks/useSessions.ts:60-66`。
- FastAPI 的 messages/advance/sessions/review 路由没有读取该 header；LangGraph command key 反而由 trace ID 生成：`app/services/langgraph_intake.py:181-188,1443-1444`、`app/api/advance.py:147-153,253-265`。
- API 文档把该 header 定义为安全提交建议项，但实现没有消费者。

网络超时或代理重试时，新的服务端 trace ID 会形成新 command，可能重复保存患者消息、重复模型调用或重复创建会话。当前测试只覆盖“同 trace/同 command”并发，不覆盖“同幂等键、不同 trace/连接重试”。

应统一写操作命令协议：优先使用经格式/长度验证的 `X-Idempotency-Key`；没有 key 时明确标为非幂等，不由 trace ID冒充；保存 request digest，稳定重放首次响应，并增加跨进程、网络超时、不同 trace 的测试。

### P1-03：公开 `/recover` 没有按 `agent_runtime` 分流

`app/api/recovery.py:46-71` 对所有会话直接调用 Legacy `RecoveryService`；服务中没有 `agent_runtime`、LangGraph `thread_id` 或 graph-version 分支。它仍读取 Legacy Redis checkpoint、PG snapshot 并直接改阶段。

这违反“既有会话不可跨运行时恢复”的迁移护栏。对 LangGraph 会话调用该 API 可能改变 `current_stage`，却没有恢复真实图游标和 pending node。

在 L5 前至少应：

- 对 LangGraph 会话先 fail closed，返回明确的 `LANGGRAPH_RECOVERY_NOT_IMPLEMENTED`；或
- 实现专用 Recovery Adapter，从持久化 runtime identity + graph version + thread ID 恢复，禁止调用 Legacy snapshot 恢复路径。

### P1-04：会话详情没有读取任何阶段结果，L3/L4 产物对前端不可见

`SessionDetailResponse` 声明了 sufficiency、syndrome、formula、safety 等字段：`app/schemas/session.py:72-101`，但 `SessionService.get_session()` 只填基础字段：`app/services/session.py:176-207`。历史测试还继续断言这些字段必须为 null：`tests/test_sessions_api.py:328-354`。

L4 产物已进入 `artifact_revision_payloads`，却没有 Read Model/DTO Adapter 把 current syndrome/formula revision 投影为兼容 DTO。前端 `StageResultsPanel` 因此只能在 mock 测试或 SSE 临时 payload 中展示结果，刷新页面后权威 GET 无法重建。

应建立版本化 Session Read Model：从 Domain tables、current artifact payload、gate 和 review/record 表组装 DTO；禁止直接依赖旧 `state_snapshot`；同时返回 `agent_runtime`、artifact revision 和 evidence mode。

### P1-05：Outbox 只有表和 lease 状态机，没有发布器，LangGraph SSE 实际断链

- Repository 只提供 `claim/acknowledge/release_failed`：`app/agent_runtime/repository.py:226-241,564-650`。
- `LangGraphIntakeMessageRunner` 接收并保存 `EventService`，但全文件没有使用 `_event_service`：`app/services/langgraph_intake.py:160-170`。
- Reasoning 服务只写 Outbox，没有调用 Redis EventService。
- 前端以 SSE stage/message 事件刷新权威详情：`frontend/src/components/ChatPanel.tsx:115-125`。

结果是 Outbox 行会持续为 pending，LangGraph 路径不会像 Legacy 一样产生 Redis Stream 事件；多客户端同步、阻断提示和阶段结果刷新依赖轮询或本次 HTTP 响应。

应实现独立 Outbox Publisher worker：事务外 claim，映射版本化业务事件到 Redis Stream，ack/retry/DLQ、退避、指标、优雅停机和重启恢复；不能在请求事务中直接双写 Redis。

### P1-06：默认质量门禁不成立，且没有 CI

- 顺序执行非 integration 集合会因迁移 fixture 顺序失败。
- 根目录 `test_agent/test_l0_1_contract.py` 不在 `pytest` 默认 `testpaths` 中；手工执行时为 `139 passed / 1 xfailed / 2 failed`。失败原因是测试仍要求 `app/agent_runtime` 只能保留 L1 骨架、禁止存在 L2–L4 业务代码，已与当前阶段冲突。
- Legacy Golden 仍有一个 strict xfail 红旗场景，L3 新链路并没有用 raw-text precheck 真正消除此风险。
- 仓库无 GitHub Actions、GitLab CI 或其他可见 CI 配置。

应重建单一门禁入口，例如：

1. `unit`: 无外部服务、必须全绿；
2. `integration`: 临时 PG/Redis/Milvus、独立数据库；
3. `contract`: L0 契约按阶段演进，过期约束显式 retire；
4. `frontend`: typecheck + lint(warnings as errors) + test + build；
5. `security`: dependency audit + secret scan + migration safety；
6. Python 3.11/3.12 矩阵。

### P1-07：模型事实的“来源验证”只验证 message ID，不验证语义落地

`_verify_sources()` 只检查输出引用的 `source_message_id` 是否属于当前消息：`app/agent_runtime/intake_verifier.py:225-246`。Observation value、red flag evidence、安全状态与消息正文之间没有 quote/span、规则匹配或二次确认关系。只要引用合法 message ID，模型幻觉出的结构化事实即可进入 Domain Reducer。

应为高风险字段增加 grounded extraction：原文 span/quote、标准化前后值、否定范围、置信度和 deterministic verifier；过敏、妊娠、当前用药、红旗必须使用模板确认或人工确认，不应凭一次模型抽取直接成为“已采集”安全事实。

### P1-08：进程级临床缓存无上限、无过期、无完成清理

- Intake：`_INTAKE_OUTPUT_CACHE`，见 `app/services/langgraph_intake.py:141`。
- Reasoning：`_SYNDROME_RESULT_CACHE`、`_FORMULA_ROUTE_CACHE`，见 `app/services/langgraph_reasoning.py:106-107`。
- 代码只有 get/set，没有 `pop`、TTL 或容量限制。

这些字典以 command/claim UUID 为 key，长期进程中会持续保留结构化临床输出；既是内存泄漏，也是超出执行期的敏感数据驻留。多 worker 又各自拥有不同 cache，行为不一致。

应优先从 durable artifact/revision 恢复；若保留加速缓存，使用有界 TTL/LRU、只保存非敏感 reference/digest，并在 claim completed/failed 后清理。增加 10k command 压测和进程重启一致性测试。

### P1-09：新版模型运行的审计/可观测性没有真正接入生产调用

`AgentRuntime` 支持 async recorder，但默认 `recorder=None`：`app/agent_runtime/runtime.py:94-106`。L3/L4 生产服务均直接构造 `AgentRuntime()`，例如 `app/services/langgraph_intake.py:813-828`、`app/services/langgraph_reasoning.py:227-246,389-409`。

- L3 成功抽取只保存 digest/count，不保存实际模型、attempt、latency、usage。
- L4 成功 artifact payload 保存 RunArtifact provenance，但失败运行仍缺少完整 episode。
- `model_actual` 实际被赋值为请求的 policy model，而不是网关响应返回的实际路由模型：`app/agent_runtime/runtime.py:149-159`。

医疗辅助系统应能回答“哪个模型、哪个 prompt/policy、何时、几次、为何失败、哪个产物被采用”。应接入持久化 recorder，记录固定字段和 digest，不保存完整 prompt/raw response；网关 DTO 应返回 actual model 和 usage。

### P1-10：前端无法自然试用新版 L3/L4

- 后端默认 runtime 仍为 Legacy，这是 L0–L8 的设计选择：`app/core/config.py:153-160`。
- 后端创建请求支持 `agent_runtime`，但前端 `SessionCreateRequest` 没有该字段：`frontend/src/types/api.ts:223-227`。
- `advanceSession()` 只有 API client 定义，仓库内没有 UI 消费者：`frontend/src/api/index.ts:270-293`。
- Session Detail 不返回 runtime 或 L4 artifact DTO。

因此“L3 可独立试用”和“L4 无 RAG 草案链”目前只能通过手工 API/测试代码体验，不能通过真实 WebUI 自然进入。L9 可以保留默认切流，但中期至少需要受控的开发/灰度入口、runtime 标签、推进按钮和只读 L4 结果卡。

## 5. P2/P3 优化项

### 5.1 性能与资源

1. **P2：checkpointer 每请求创建、setup、编译图、关闭连接池。** messages 为 `app/services/langgraph_intake.py:198-210`，advance 为 `app/api/advance.py:174-186`。应在 lifespan 初始化共享 saver/pool 和 compiled graph；启动时 setup/health，停机统一关闭。
