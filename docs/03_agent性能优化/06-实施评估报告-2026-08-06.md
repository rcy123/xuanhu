| 维度 | Formula RAG（base） | Modification RAG（加减） |
|------|---------------------|--------------------------|
| sources | `("formula", "herb", "case")` | `("herb", "case")` |

- **Smoke test**：`MODIFICATION_PRIMARY_SOURCES` 与 `FORMULA_PRIMARY_SOURCES` 确认不同（`('herb', 'case')` vs `('formula', 'herb', 'case')`）
- **`build_modification_query`**：正确拼接基础方名、组成、证型、待调症状
- **向后兼容**：Formula RAG 路径完全未变；当 `retriever=None`（测试缺省）走空证据降级模式

### 变更内容

| 文件 | 变更 |
|------|------|
| [formula.py](../../app/schemas/formula.py) | 新增 `BaseFormulaAlternative` schema、`BaseFormulaDraft.alternatives` 字段、`ModificationDraftInput.modification_query_hint` 字段 |

| [langgraph_reasoning.py](../../app/services/langgraph_reasoning.py) | 多方案并行 modification：`asyncio.gather(*mod_tasks)`，首成功提交为主结果 |
| [base_formula_draft_rag_v1.jinja2](../../app/agents/prompts/base_formula_draft_rag_v1.jinja2) | 新增 alternatives 多方案输出指引（≥2 套、不同 angle、modification_query 提示） |
| [modification_draft_rag_v1.jinja2](../../app/agents/prompts/modification_draft_rag_v1.jinja2) | 新增 modification_query_hint 加减检索方向指引 |

### 核心逻辑

```
BaseFormulaDraft:
  alternatives: [
    {formula: F1, angle: "偏重祛风止痛", confidence: 0.88, modification_query: "检索头痛加减相关医案"},
    {formula: F2, angle: "偏重祛风除湿", confidence: 0.65, modification_query: "检索祛风除湿类本草证据"},
    {formula: F3, angle: "偏重调和营卫", confidence: 0.42, modification_query: "..."},
  ]

filter_alternatives(threshold=0.45, min_keep=1, max_keep=3):
  → 保留 F1 (0.88), F2 (0.65) — F3 低于阈值被裁掉
  → 并行执行 F1.modification + F2.modification（asyncio.gather，延迟不叠加）
  → 首成功结果作为主提交，其余存入 intermediate data 供前端展示
```

### 置信度筛选规则

1. 按置信度降序排列
2. 过滤低于阈值的方案（默认 `base_formula_confidence_threshold=0.45`）
3. 至少保留 `min_keep` 套（默认 1，即使全部低于阈值也保底）
4. 最多保留 `max_keep` 套（默认 3）

### 向后兼容

- `alternatives` 为空时（旧 prompt 行为），编排层从 `base_formula` 构造单元素列表
- `base_formula` 字段保持不变，始终等于 `alternatives[0].formula`
- `modification_query_hint` 为空/不存在时，加减模型按常规流程处理
- Prompt 模板仅修改 RAG 版本（`_rag_v1.jinja2`），no-RAG 模板未动

### 验证结果

- **单元测试**：41 个 formula draft 测试全部通过（含 schema 校验、preflight、verifier、boundary）
- **Smoke test**：`filter_alternatives()` 阈值筛选、保底、封顶逻辑均正确
- **Schema 约束**：`alternatives` 字段 `min_length=0, max_length=4`，`BaseFormulaAlternative` 含 `formula`/`angle`/`rationale`/`confidence`/`modification_query`

### 待验证（需真实后端）

- [ ] 一次全链路 reasoning 流量验证多方案 prompt 引导下 LLM 确实输出 ≥2 套方案
- [ ] 验证不同方案的 `modification_query` 确实引导加减模型产生差异化的加减结果
- [ ] 验证并行 modification 的延迟改善（期望：多方案延迟 = max(单方案延迟)，而非 sum）

### 变更内容

| 文件 | 变更 |
|------|------|

### 核心逻辑

```
原始 query（key=value 拼接）:
  chief_complaint.symptom=头痛3天；tongue_coating.color=苔薄白；pulse_manifestation.type=脉浮紧...

LLM 改写后（医学叙事）:
  患者头痛3天，苔薄白，脉浮紧，伴发热...辨证属风寒束表证，治以辛温解表...
```

### 功能开关

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `rag_query_rewrite_enabled` | `False` | 关闭时走原始 `build_syndrome_query()` |
| `rag_query_rewrite_model` | `""` | 为空时复用 `chat_model` |

### 验证结果

- **单元测试**：24 个 syndrome draft 测试全部通过（含 preflight、verifier、gate check）

- **降级安全**：`rewrite_syndrome_query()` 在 gateway 为 None 或 LLM 调用失败时自动 fallback 到 `build_syndrome_query()`
- **Prompt 质量**：system prompt 明确要求"医学病例叙事风格"输出，不含指令注入风险

## 4. Reranker 升级

### 变更内容

| 文件 | 变更 |
|------|------|
| [reranker.py](../../app/rag/reranker.py) | 新增 `cross_encoder_rerank()`、`llm_rerank()`、`_call_reranker_api()`、`_parse_llm_rerank_scores()` |
| [reranker_gateway.py](../../app/core/reranker_gateway.py) | **新文件**：Reranker 专用模型网关配置（遵循 `embedding_gateway.py` 的 `SimpleNamespace` 模式） |
| [retriever.py](../../app/rag/retriever.py) | `hybrid_search` 支持 `rag_reranker_enabled` 开关，路由到 Cross-Encoder / LLM Reranker |
| [config.py](../../app/core/config.py) | 新增 7 个 reranker 配置项 + 5 个 reranker gateway 配置项 |

### 两种 Reranker 对比

| 维度 | Cross-Encoder | LLM Reranker |
|------|---------------|--------------|
| 原理 | 专用模型对 (query, chunk) 逐对打分 | LLM 一次性对 N 个 chunks 打 0-10 分 |
| 精度 | 高（专用训练） | 最高（中医语义理解） |
| 延迟 | 低（~100ms） | 中-高（~500-2000ms） |
| 成本 | 低（本地/专用 API） | 中（LLM token 消耗） |
| 部署依赖 | 需要 reranker 模型服务 | 复用现有 LLM 网关 |
| 降级路径 | → MVP 加权求和 | → MVP 加权求和 |

### 功能开关

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `rag_reranker_enabled` | `False` | 关闭时走 MVP 加权求和 |
| `rag_reranker_provider` | `"cross_encoder"` | `cross_encoder` 或 `llm` |
| `rag_reranker_model` | `""` | 为空时 Cross-Encoder 用 `jina-reranker-m0`；LLM 复用 `chat_model` |

### 验证结果

- **Smoke test**：`_parse_llm_rerank_scores()` 正常解析 JSON `{"scores": [...]}` 和垃圾输入 fallback
- **`cross_encoder_rerank()`**：调用 `_call_reranker_api()` POST `/rerank`，支持 Jina-style 和 OpenAI-style 响应格式解析
- **`llm_rerank()`**：通过 `gateway.chat()` 调用 LLM 打分，temperature=0.0 保证确定性
- **降级安全**：API 调用失败 → 自动 fallback 到 MVP `rerank()`
- **Reranker Gateway**：`build_reranker_gateway_settings()` 在 `reranker_gateway_base_url` 为空时自动回退主模型网关
- **仅在有足够候选时激活**：`hybrid_search` 在 `enough candidates (>= top_k*2)` 时才走 reranker，候选不足直接走 MVP

### 待验证（需真实后端 A/B 评测）

- [ ] 部署 Cross-Encoder 模型服务（推荐 `jina-reranker-m0` 或 `bge-reranker-v2-m3`）
- [ ] 配置 `RERANKER_GATEWAY_BASE_URL` 指向 reranker 服务
- [ ] 对比 MVP vs Cross-Encoder vs LLM Reranker 的 Top-K 检索质量（NDCG、hit rate）
- [ ] 评估 Cross-Encoder 延迟（期望 < 200ms）和 LLM Reranker 延迟（期望 < 2s）
- [ ] 评估 LLM Reranker 的分数稳定性（同一 query 多次打分的一致性）
