## OP1 · 状态下推子图（关联 H1 H2 M10）

### 1.1 现状

- `XuanhuGraphState` 已有 `domain_state_version` 字段,但未挂载完整 DomainState 实体,只是版本号。
- reasoning 子图每个节点都 `repository.get_state(claim.session_id)`（[langgraph_reasoning.py:516-1664](app/services/langgraph_reasoning.py#L516)）,单 claim 10 处 DB round-trip。
- intake `_finalize_intake_route` 对 ready/incomplete/conflict/manual 四路由各跑一遍 `_compute_intake_from_claim`（[langgraph_intake.py:2718-2914](app/services/langgraph_intake.py#L2718)）。
- `evaluate_raw_text_triage_precheck` 同一 claim 多节点各跑一次（M10）。

### 1.2 方案

**(a) DomainState 进入图状态**:
在 `XuanhuGraphState` 增字段 `domain_state_snapshot: DomainState | None`（或内存对象句柄,不序列化进 checkpoint——见风险)。reasoning 子图入口节点（`precheck`）加载一次 `get_state`,写入 snapshot。下游 `build_syndrome_context`/`draft_syndrome`/`verify_syndrome`/`build_formula_context`/`draft_formula` 读 snapshot 而非再查库。

```
Before: precheck→build_ctx→draft→verify→build_ctx→draft→verify
         [get_state 10 次,跨 7 节点]
After:  precheck(加载1次,写snapshot) → 后续节点读snapshot(0 DB)
```

**(b) `_compute_intake_from_claim` 复用**:
intake 计算结果（reduce 后的 intake output + completeness gate + category）只算一次,随 `claim.intermediate_payload` 持久化。 `_finalize_intake_route` 的四路由读取该结果而非重算。

**(c) triage_precheck 结果缓存**:
`evaluate_raw_text_triage_precheck` 结果在 `triage_precheck` 节点算一次,记入 `claim.intermediate_payload["triage_precheck"]`,后续节点（extract/verify/reduce/gates/finalize）读缓存。

### 1.3 checkpoint 兼容性（关键风险）

LangGraph 会把 state 序列化进 Postgres checkpointer。若 `domain_state_snapshot` 装大对象+进序列化,会:
1. bloat checkpoint 表;
2. 反序列化时跨进程类型重建失败。

**对策**:snapshot 字段标记为 `transient=True`(LangGraph reducer 支持),**不进 checkpoint**,只在当前运行链路内传递。若运行跨中断(ReviewSubgraph 中断后 resume),恢复时重新触发一次入口加载——可接受,因 resume 本就是低频路径。

### 1.4 不破坏的契约

- 不改 API envelope / 错误码 / SSE 事件 schema。
- 不改 LLM 调用语义(同 prompt、同 model、同 max_tokens)。
- 不改 artifact 落库模型。
- 改的是"同一个事实在内存中传递几次,而非查库几次"。

### 1.5 隐含的 N+1 防护

OP1 让节点读 snapshot 而非再 lazy 触发关系加载;但若 snapshot 只取主实体,而某个节点仍访问 `.messages`/`.agent_runs` 等关系(全用 `lazy="raise"`),会抛错。因此 OP1 实施时**连带为本期路径加 `selectinload`**(M7 子集),否则 snapshot 反而暴露新报错。这部分 N+1 治理归入 OP1 验收门禁,不单独立块。

### 1.6 预期收益

- 单 claim DB round-trip:10+ → 1-2(reasoning),4 → 1(intake finalize)。
- 按 reasoning 7 节点估算,纯 DB 往返(PG async + 序列化)省约 60-70%。
- 量化靠 OP4 埋点:`reasoning.get_state.total_db_ms` histogram 前/后对比。

## OP2 · 网关连接池化 + embedding 缓存（关联 H3 H4,顺带 M5）

### 2.1 现状

- `ModelGatewayClient._request_with_retry` 每次重试 attempt 都 `async with httpx.AsyncClient(...) as client:`（[gateway.py:216-224](app/core/gateway.py#L216)）,DNS/TLS 握手重复。
- `_vector_search` 每次 `await self._gateway.embed([query], ...)`,无缓存（[retriever.py:389-392](app/rag/retriever.py#L389)）。
- structured 输出 fallback 最坏 7 次请求（M5),bounded 路径已 `max_requests=1`,legacy 路径未关。

### 2.2 方案

**(a) httpx.AsyncClient 提为实例成员**:
`ModelGatewayClient.__init__` 持有一个 `httpx.AsyncClient` 实例,配 `httpx.Limits(max_connections=64, max_keepalive_connections=16, keepalive_expiry=30.0)`。`_request_with_retry` 复用而非 `async with`。生命周期由 `app.state` 管理:启动时构造、关闭时 `await client.aclose()`,跟 `shared_langgraph_runtime` 同款 lifespan 模式（[lifecycle.py:113-170](app/agent_runtime/lifecycle.py#L113)）。
- 嵌入式 embedding client 同样处理（embedding_gateway.py）,或共享主 client(若 endpoint 同域)。

**(b) embedding 缓存**:
`RAGRetriever._vector_search` 之前,新增 `EmbeddingCache`(`app/rag/embedding_cache.py`):
- key = `sha1(query_text)`。
- value = embedding vector(list[float])。
- store = Redis(已有 `app/core/redis.py` 单例)。
- TTL = 1 小时(问诊 query 重复度高)。
- 命中即跳 `self._gateway.embed`。

只缓存 query embedding,**不缓存**文档侧 embedding(那是离线 sync 脚本产物,在线不重算)。

**(c) 关闭 legacy structured fallback(M5)**:
审查 `chat_structured` 全调用点,强制 `max_requests=1`,移除 `json_object` fallback 在 legacy 路径的使用。本项**风险**:legacy 路径可能依赖 fallback 提高解析成功率,移除前需在预发布跑回归(见 99 文档)。

### 2.3 不破坏的契约

- 不改 `ModelGatewayClient` 对外 API(`chat`/`chat_structured`/`embed` 签名不变)。
- 不改 token 观测(`model_run_audit` 落库逻辑不变)。
- 不改 header sanitization 与 structured output host 分流。

### 2.4 预期收益

- 握手开销:N 次 → 1 次/进程(连接池复用)。高 QPS 下 RTT 上涨收敛。
- embedding RTT:缓存命中 → 0(对比一次网关 RTT ~ 50-200ms)。
- tail latency:关 legacy fallback 后,最坏从 7 请求 → 3 请求。

## OP3 · Milvus 异步化 + 共享 client（关联 H5 H6,可选 M1）

### 3.1 现状

- `milvus.search(**search_params)` 同步阻塞调用包在 async 里（[retriever.py:409](app/rag/retriever.py#L409)）。
- `RAGRetriever` 每节点新建实例 → Milvus client 每节点重建 gRPC channel（[reasoning_retrieval.py:287-301](app/rag/reasoning_retrieval.py#L287)）。
- health 检查每次新建 Milvus client（[health.py:225-287](app/services/health.py#L225)）。
- 向量命中后单独 PG round-trip 回填 content（M1, [retriever.py:560-597](app/rag/retriever.py#L560)）。

### 3.2 方案

**(a) `asyncio.to_thread` 包同步 search**:
`_vector_search` 内:
```python
results = await asyncio.to_thread(milvus.search, **search_params)
```
pymilvus 当前无成熟 async 接口,`to_thread` 是最低侵入方案。同理 `health.py` 的 `_check_milvus`/`_check_milvus_collection`(L222-301) 也包 `to_thread`。

**(b) Milvus client 进程单例**:
在 `app.state` 注册共享 `MilvusClient`(或共享 `RAGRetriever`),跟 lifespan 启停,类比 `shared_langgraph_runtime`。`_rag_retriever()` 从 `app.state.rag_retriever` 取,而非 `return RAGRetriever()`。

**(c) output_fields 含 content（M1，纳入本期）**:
Milvus search 的 `output_fields` 加 `content`,省 PG 回填往返。**注意**:Milvus 单字段大小 + collection 膨胀权衡,实施时先测一下 chunk content 平均大小(确认无超大 blob 字段),测完直接落地。命中后 `_backfill_content_snippets` 改为优先读 Milvus `output_fields` 的 content,缺省回退到原 PG 路径(向后兼容)。

### 3.3 不破坏的契约

- 不改 `RAGRetriever.retrieve` / `hybrid_search` 对外签名。
- 不改 `_backfill_content_snippets` 在 content 未含时的回退路径(向后兼容)。
- 不改 health 端点 schema(只改实现是异步的)。

### 3.4 预期收益

- 事件循环不再被 Milvus 阻塞,并发请求吞吐上限打开(从"单线程串行向量检索" → "并行 to_thread")。
- 连接建立:gRPC channel 每节点重建 → 进程单例。
- OP4 埋点可测 `milvus.search.p95` 前/后并发吞吐(并发 N 路检索的总延迟)。

## OP4 · per-stage 延迟埋点 + Prometheus histogram（关联 H7）

### 4.1 现状

- `gateway.py` / `retriever.py` 只有 `logger.info(...) hits=`,不记耗时。
- 无 OpenTelemetry/Prometheus histogram。
- 唯一 P50/P95 在测试 `tests/golden/test_langgraph_performance_baseline.py:66-159`,不覆盖 RAG、不上生产。

### 4.2 方案

**(a) 新增 `app/core/metrics.py`**:
用 prometheus_client(项目已用 Prometheus,见 `outbox_metrics.py`)定义 histogram:
```python
RAG_VECTOR_SEARCH = Histogram("xuanhu_rag_vector_search_seconds", ...)
RAG_FULLTEXT_SEARCH = Histogram("xuanhu_rag_fulltext_search_seconds", ...)
RAG_BACKFILL = Histogram("xuanhu_rag_backfill_seconds", ...)
RAG_EMBED = Histogram("xuanhu_rag_embed_seconds", ...)
GATEWAY_CHAT = Histogram("xuanhu_gateway_chat_seconds", labels=["host","route_profile"])
GATEWAY_EMBED = Histogram("xuanhu_gateway_embed_seconds", ...)
GRAPH_NODE = Histogram("xuanhu_graph_node_seconds", labels=["subgraph","node"])
REASONING_GET_STATE = Histogram("xuanhu_reasoning_get_state_seconds", ...)
```
buckets 按 0.01/0.05/0.1/0.25/0.5/1/2.5/5/10/30 切。

**(b) 计时装饰器/上下文**:
提供 `measure(stage_name)` async context manager,`async with measure("rag.vector") as m: ...`,结束时 `M.observe(elapsed)`。比手写 `perf_counter` 整洁、不漏点。

**(c) 暴露端点**:
新增 `GET /api/v1/metrics/perf`(类比已有 `/api/v1/metrics/outbox`),prometheus_client `generate_latest` 输出。Phase 1 阶段可放任该端点无鉴权(同为 Prometheus 抓取形态),或一次性纳入加固文档的健康检查豁免清单。

**(d) baseline 落地**:
埋点铺完后,在预发布跑一轮真实流量(或压测脚本 `scripts/perf_baseline.py`)采集 P50/P95,作为后续 OP1-3 改造的 before 基线。OP1-3 完成后再采一轮 after,写入 99 文档的对比表。

### 4.3 隐私与脱敏

- histogram 只记耗时不记内容,不泄露 PHI。
- 不在 label 里放 session_id/patient_ref(高基数 + 泄露风险)。
- label 只用低基数项:`subgraph` / `node` / `host` / `route_profile`。

### 4.4 预期收益

- 把"我做了优化"变成"我证明 P95 从 X 降到 Y"。
- 生产可持续观测性能回归(CI 加 histogram snapshot diff, 防 N+1 回归)。
- README 的"性能"一节有真实数字。
