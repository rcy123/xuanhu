# 性能诊断报告 · 悬壶 Xuanhu

> 状态：调研定稿
> 方法：三路并行调研（Explore agent），分别覆盖 ①LangGraph agent 编排并发模型 ②SSE+DB 异步链路 ③RAG 检索+模型网关延迟
> 口径：每条缺陷带文件:行号、影响级别（高/中/低）、优化方向

---

## 0. 核心判断

**瓶颈不在 LLM 本身,而在"无谓的重复 DB round-trip + 事件循环里混同步阻塞 + 连接池红利全没拿到 + 零生产可观测性"。**

LLM 调用已被作者用 TTL 缓存（`_INTAKE_OUTPUT_CACHE` / `_SYNDROME_RESULT_CACHE`，`ephemeral_cache.py` BoundedTTLCache(256, 300s)）+ artifact 落库-恢复机制保护——**未发现重复 LLM 浪费**。这部分设计是对的，本次优化不动。

主图拓扑：`START → command_router → conditional_edges → 四子图之一 → END`。子图互斥（`route_after_router` 只返回一个目标），子图内全部 `add_edge` 线性链 + 条件边，全仓 0 处 `Send` / `asyncio.gather` / `TaskGroup`。

## 1. 🔴 高 ROI 缺陷（H1-H7）

### H1 · reasoning 子图每个节点都 `repository.get_state()`

- **位置**：[langgraph_reasoning.py:516,550,584,699,737,1236,1313,1513,1598,1664](app/services/langgraph_reasoning.py#L516)
- **现象**：`PostgresDomainRepository(get_session_factory()).get_state(claim.session_id)` 在 reasoning 子图几乎每个节点都调一次。`_current_authority`（L1309-1314）一次 `get_state` + 一次 `get_reasoning_authority`,被 precheck/build_syndrome/build_formula/draft_syndrome 多次调用。`_syndrome_graph_update`/`verify_syndrome` 还单独再调一次只为拿 `state_version`。
- **影响**：**高**。单 claim 累计 10 处 DB round-trip,加载同一 DomainState。
- **优化方向**：节点入口把 DomainState / authority snapshot 写进 `XuanhuGraphState`（已有 `domain_state_version` 字段可挂载成进程内缓存），下游节点直接读 state。DB round-trip 可降 60%+。

### H2 · intake 四路由各重算 `_compute_intake_from_claim`

- **位置**：[langgraph_intake.py:2718-2914](app/services/langgraph_intake.py#L2718) `_finalize_intake_route`
- **现象**：对 ready/incomplete/conflict/manual 四个 route 节点各重新跑一遍 `reduce_domain_state` + `evaluate_completeness_policy` + `_classify_and_merge_category`。
- **影响**：**高**。同一份 intake 计算被算 4 次。
- **优化方向**：只算一次，结果随 `intermediate` 持久化，四路由共享。

### H3 · `httpx.AsyncClient` 每次请求新建

- **位置**：[gateway.py:216-224](app/core/gateway.py#L216) `_request_with_retry`
- **现象**：重试循环内每次 attempt 都 `async with httpx.AsyncClient(...) as client:` 新建客户端。`ModelGatewayClient.__init__` 不持有任何 client 实例；`health_check`（L957-1007）也每次新建。
- **影响**：**高**。每次请求重走 DNS/连接建立/TLS 握手,连接池完全失效。高 QPS 下端口耗尽、RTT 上涨显著。
- **优化方向**：client 提为 `ModelGatewayClient` 实例成员或模块级单例,跟 lifespan 启停,配 `httpx.Limits(max_connections, max_keepalive_connections)`。

### H4 · 每次 query 实时 embedding,无缓存

- **位置**：[retriever.py:389-392](app/rag/retriever.py#L389) `_vector_search`
- **现象**：`await self._gateway.embed([query], trace_id=...)` 每次重新生成 embedding。全仓无 embedding 缓存实现。
- **影响**：**高**。每次 RAG 检索多一次 embedding 网关 RTT。问诊 query 高度同质(常见症状),命中率应很高。
- **优化方向**：query 文本 hash → Redis 缓存 embedding（TTL）,尤其 `build_syndrome_query`/`build_formula_query` 输出文本结构化、命中率高。

### H5 · Milvus `search()` 同步阻塞包在 async 里

- **位置**：[retriever.py:409](app/rag/retriever.py#L409)；同步导致 [health.py:222-301](app/services/health.py#L222) 也受影响
- **现象**：`milvus.search(**search_params)` 是 pymilvus 同步 SDK,包在 async coroutines 里但未 `run_in_executor`,直接阻塞事件循环线程。
- **影响**：**高**。并发请求下,单次向量检索卡住整个事件循环。
- **优化方向**：`asyncio.to_thread(milvus.search, ...)` 或迁移 pymilvus async 接口。

### H6 · `RAGRetriever` / Milvus client 不共享,每节点重建

- **位置**：[reasoning_retrieval.py:287-301](app/rag/reasoning_retrieval.py#L287) `_rag_retriever()` 每次 `return RAGRetriever()`；[langgraph_reasoning.py:618,820](app/services/langgraph_reasoning.py#L618) 每节点调用；[health.py:225-287](app/services/health.py#L225) 每次健康检查新建
- **现象**：`RAGRetriever` 实例级懒加载 Milvus client（`_get_milvus_client` L205-214）,但实例本身每次新建 → 每节点触发新 `MilvusClient(uri, timeout=30)` gRPC channel 初始化。同会话 syndrome+formula 两阶段 = 2 个独立 client。
- **影响**：**高**。每个 reasoning 节点 = 一个新 Milvus 长连接,连接建立不是 zero-cost。
- **优化方向**：`app.state` 注册共享 `RAGRetriever`（或至少共享 `MilvusClient`),跟 lifespan 启停,类比已有 `outbox_publisher` 模式（main.py:76-87）。

### H7 · 零生产延迟可观测性

- **位置**：全仓业务侧无 `histogram` / `duration.*observe`(仅测试/文档命中)
- **现象**：`gateway.py` 只有 `logger.info("chat 完成: ...")` 不记耗时；`retriever.py` 同样只记 hits 数不记耗时。无 OpenTelemetry/Prometheus histogram。`outbox_metrics.py` 仅暴露 outbox gauges。`tests/golden/test_langgraph_performance_baseline.py:66-159` 是唯一 P50/P95 计算,仅测 L3 intake 整消息 RT,不覆盖 RAG、不上生产。
- **影响**：**高**。无法从生产观测回答"RAG P95 在哪一阶段",只能靠结构化日志事后 grep。优化效果无法量化证明。
- **优化方向**：`_vector_search`/`_fulltext_search`/`_backfill_content_snippets`/`gateway._request_with_retry`/`embed` 各加 `time.perf_counter` 埋点,通过现有 Prometheus exposition(`/api/v1/metrics/outbox` 同款机制)暴露 histogram。

## 2. 🟡 中 ROI 缺陷（M1-M11）

### M1 · 向量命中后单独一次 PG round-trip 回填 content

- **位置**：[retriever.py:560-597](app/rag/retriever.py#L560) `_backfill_content_snippets`
- **现象**：Milvus `output_fields` 现取 `["chunk_id","source_type","source_id","title","content_hash"]`（L405）不含 content,命中后另查 PG 拉完整 content,多一次 DB 往返。
- **优化**：让 Milvus `output_fields` 直接含 content,省一次 DB。（注意 Milvus blob 字段大小权衡)

### M2 · `_load_herb_normalizer` 每次开方全表 select Herb

- **位置**：[langgraph_reasoning.py:380-390](app/services/langgraph_reasoning.py#L380)
- **优化**：进程级 LRU(herbs 表变化少)。

### M3 · `AgentRuntime` 每节点重新构造

- **位置**：langgraph_intake.py:890,1219,1473,1500,1657 等;langgraph_reasoning.py:613,628,814,891 等
- **现象**：每次实例化 `import PostgresModelRunRecorder`(runtime.py:184) + 新 `ModelGatewayClient(max_retries=0)`。
- **优化**：`shared_runtime`（lifecycle.py)挂 process 单例。

### M4 · recorder 四事件每节点 2 次 async IO 串行 await

- **位置**：[runtime.py:91-136](app/agent_runtime/runtime.py#L91)；`RECORDER_TIMEOUT_SECONDS = 0.05`(L56)
- **现象**：started/succeeded/failed/cancelled 各 `create_task + shield + wait_for`,成功路径 2 次 IO 串行 await,累计可能 100ms+。
- **优化**：合并为单 audit 行(用 status 字段区分),或 started 异步 fire-and-forget 不 await。

### M5 · structured 输出双层重试 + json_object fallback

- **位置**：[gateway.py:475-751](app/core/gateway.py#L475)
- **现象**：`_chat_structured_impl` 外层解析失败重试循环(L475-645)+ 内层 HTTP 重试 + `json_object` fallback(L627-641,671-751)再发一整次请求(注释明确 14s+14s)。最坏 7 次请求。bounded caller 已传 `max_requests=1`(L620-621)关 fallback,但 legacy/non-runtime 路径未受限。
- **优化**：全 `chat_structured` 调用点强制 `max_requests=1`,剔除 legacy fallback。

### M6 · 子图节点串行,可并发的 precheck 却串行

- **位置**：[intake_subgraph.py:199-237](app/agent_runtime/intake_subgraph.py#L199) / [reasoning_subgraph.py:172-198](app/agent_runtime/reasoning_subgraph.py#L172)
- **现象**：`build_context` 与 `triage_precheck`/`clarify_precheck` 互不依赖却串行。
- **优化**：`asyncio.gather` 并发 precheck 节点(LangGraph 支持 fan-out 到无依赖节点,但需改拓扑,谨慎)。

### M7 · 全仓 0 处 `selectinload`/`joinedload`,`lazy="raise"` 把 N+1 变成"运行时错"

- **位置**：[models/*.py](app/models/) 全用 `lazy="raise"`(consult.py:51-66,agent.py:47-56,knowledge.py:38-41,79,139,235,286,safety.py:48,review.py:51)
- **现象**：`lazy="raise"` 阻止隐式 N+1,但任何需要关系数据的查询必须显式 eager-load,仓库内却没用 `selectinload`/`joinedload`。等于"运行时报错或被迫手动二次查询"。
- **优化**：审查 `app/agent_runtime/repository.py:652,718,786,792,1132-1192,1269,1294,1613,1724,1751` 等所有 `select(Entity).where(...)`,凡是读后访问关系的加 `selectinload`。

### M8 · SSE 长连接无并发上限、无背压

- **位置**：[events.py:339-366](app/services/events.py#L339) `iter_sse`
- **现象**：`while True` 无限循环直到断连,Redis `XREAD BLOCK` 每 30s 心跳。无最大连接数/per-session 互斥;慢客户端只靠 Redis Stream `MAXLEN ~ 1000`(events.py:31)裁剪。每一个挂着的长连接占用一个 ASGI worker + 一条 Redis 阻塞读。
- **优化**：最大并发连接数/per-session 互斥;客户端消费缓慢时主动关闭流;`write()` 显式 timeout。

### M9 · outbox polling 0.5s 空载成本

- **位置**：[config.py:252](app/core/config.py#L252) `outbox_publisher_poll_interval_seconds = 0.5`;[outbox_publisher.py:323-337](app/services/outbox_publisher.py#L323) `run_forever`
- **现象**：空批时每 0.5s 一次 `SELECT ... FOR UPDATE SKIP LOCKED LIMIT 50`。`claim`(repository.py:964-993)实现正确无重复消费,但空载每秒 2 次 PG 往返。
- **优化**：高优先级事件用 PG `LISTEN/NOTIFY` 触发立即 `run_once`,平时拉长 polling 至 2-5s;验证 `status+available_at` 上有部分索引。

### M10 · 重复 `evaluate_raw_text_triage_precheck`

- **位置**：[langgraph_intake.py:1483,1553,2246,2420,2554](app/services/langgraph_intake.py#L1483)
- **现象**：纯正则函数(不调 LLM),但同一 claim 多节点各跑一次,每个 finalize route 经 `_compute_intake_from_claim` 触发重复。
- **优化**：随 `claim.intermediate_payload` 缓存一次,节点间共享。

### M11 · Redis 未设 `max_connections`

- **位置**：[redis.py:46-53](app/core/redis.py#L46)
- **现象**:`Redis.from_url` 未显式声明连接池上限。每请求一次 ping(L37-39,开销小但存在)。
- **优化**：显式 `max_connections`。
