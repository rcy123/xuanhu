# 00 · 并发吞吐与稳定性优化方案

> 状态：**阶段 1~2、阶段 4 已实施**（阶段 3、阶段 5 方案稿，待评审）
> 适用范围：**多用户并发上线前**的吞吐与稳定性优化
> 前置依赖：04_生产环境加固 已实施（认证/授权/访问隔离/限流/密钥守卫均已落地）
> 执行方式：**先文档、再实现、分阶段灰度**

---

## 1. 背景与结论摘要

悬壶已完成功能闭环（问诊→辨证→开方→安全审核→医师确认→病历）与生产加固（JWT 认证、多账号角色、会话所有权隔离、限流、密钥守卫）。在此基础上对**并发承载能力**做了设计层评估，得到两个看似矛盾、实则一致的结论：

1. **系统"不会因并发高而崩溃"**：async 单线程 + 会话级锁 + 各资源池硬上限 + 超时/重试/降级兜底，保证了并发安全。
2. **系统"业务吞吐被单点串行卡死"**：R7 异步命令 worker 是单实例且**串行**处理命令，而一次"辨证开方"要串行 3 次模型调用，导致全系统吞吐上限极低。

> ⚠️ **关键反直觉事实**：当前单进程部署下，R7 异步路径（单 worker 串行）的业务吞吐 **反而低于** 同步回退路径（多请求并发 + DB 连接池并行）。R7 异步的价值是"HTTP 快速返回、可重试、幂等"，但吞吐上被单 worker 串行抵消了。

本方案分 5 个阶段，按"投入产出比"排序，先解决吞吐核心，再补横向扩展与可观测性。

## 4. 阶段 1：R7 worker 并发消费（P0-1）

### 解决什么问题

全系统开方吞吐被单 worker 串行限制在 ≈ 1~4 次/分钟。这是当前最大的吞吐瓶颈——**只要模型网关有 64 连接的能力，串行消费就是浪费**。

### 方案

在 `app/agent_runtime/async_command_worker.py` 的 `run_once()` 中，把"逐个 `await`"改为"受并发上限约束的 `asyncio.gather`"：

```python
async def run_once(self) -> WorkerRunResult:
    claimed = await self._repository.claim(...)
    semaphore = asyncio.Semaphore(self._max_concurrency)  # 建议 8~16

    async def bounded(command):
        async with semaphore:
            return await self._process(command)

    outcomes = await asyncio.gather(*(bounded(c) for c in claimed))
    ...
```

配套改动：

1. 新增配置 `ASYNC_COMMAND_MAX_CONCURRENCY`（默认 8，范围 1~32）。
2. **保持会话级串行语义**：命令处理内部仍走 PG advisory 会话锁，同一会话的命令即使并发 claim 也会被锁串行化，不同会话的命令真正并行。
3. heartbeat 逻辑需改为"处理期间持续心跳"，不能因并发处理而跳过心跳续租（lease=60s，命令最坏 180s，必须有续租）。
4. 单命令失败隔离：`gather(return_exceptions=True)` 或逐命令 try/except，一个命令失败不影响同批其他命令。

### 预期收益

- 吞吐从 ≈ 1~4 次/分钟 提升到 **≈ 8~16 次/分钟**（受并发上限与模型网关连接池共同决定）。
- 完全兼容现有幂等/重试/outbox 事件契约，**不改变任何 API 语义**。

### 风险与回退

| 风险 | 缓解 |
|---|---|
| 并发把模型网关/DB 打爆 | 并发上限从 8 起步，实测后上调；DB 连接池先配合扩（见阶段 3） |
| 同一会话命令并发处理语义变化 | 依赖已有 PG advisory 锁兜底；补并发同会话集成测试 |
| 命令失败互相干扰 | `return_exceptions=True` + 逐命令独立落错误状态 |

## 5. 阶段 2：多 worker / 多进程横向扩展（P0-2）

### 解决什么问题

单进程 uvicorn 是吞吐与内存的单点上限；多医师并发时无法利用多核。

### 方案

1. 用 `uvicorn --workers N`（或 gunicorn + uvicorn worker）启动 N 个进程，N 建议 = CPU 核数（内网 2~4 起步）。
2. 确认以下机制在**多进程下仍然安全**（评估已确认，需补验证）：
   - 异步命令 worker：`claim` 用 `SELECT ... FOR UPDATE SKIP LOCKED`，多进程不会重复认领同一命令；
   - 会话锁：PG advisory lock 天然多进程安全（R8-A 注释已声明）；
   - outbox publisher：同样 `skip_locked`；
   - Redis 连接：每进程各自持有，无跨进程共享问题。
3. 每个进程拥有独立的模型网关连接池（64），总连接能力 = N × 64，需与模型网关侧承受能力匹配。
4. 在 `deploy/` 补 uvicorn worker 数量的启动命令与文档。

### 预期收益

- 业务吞吐随 worker 数量近似线性扩展（阶段 1 的并发消费 × N 进程）。
- 单进程崩溃不再导致全站不可用（需配合反向代理的健康检查/重试）。

### 风险与回退

| 风险 | 缓解 |
|---|---|
| 多进程共享 PG/Redis 的竞争 | 全部走已有 `skip_locked` + advisory lock，已设计为多进程安全 |
| 模型网关连接数翻倍 | 与网关侧确认连接上限，必要时降低每进程 httpx 池 |
| 会话锁跨进程 | PG advisory lock 是权威后端，跨进程唯一 |

## 6. 阶段 3：连接池 / 超时 / SSE 分离调优（P1-1/P1-2/P1-3）

### 解决什么问题

并发上来后，DB 30 连接会成为次瓶颈；模型网关慢会放大积压；SSE 长连接会挤占短请求资源。

### 方案

1. **DB 连接池**：`pool_size` 按 `worker 数 × 8` 上调（如 4 worker → `pool_size=32, max_overflow=32`），同步确认 PG `max_connections` 足够。
2. **模型网关超时分级**：
   - 辨证/开方等长生成：保留 60s；
   - 问诊改写/reranker 等短调用：已有多网关超时覆盖（`rag_query_rewrite_timeout_seconds` 等），确认配置合理。
3. **SSE 分离**：
   - nginx 层把 `/stream` 路由到独立 location（已配 `proxy_buffering off`，补 `keepalive` 与连接数上限）；
   - 或未来把 SSE 拆到独立进程/服务，避免与短请求抢 worker。
4. **连接池监控**：暴露 DB/httpx 池的当前使用率指标（阶段 4 消费）。

### 预期收益

- 消除 DB 连接池这个次瓶颈，让并发 worker 有足够连接可用。
- SSE 不再挤占短请求资源。

### 风险与回退

| 风险 | 缓解 |
|---|---|
| DB 连接上调超出 PG 规格 | 先查 PG `max_connections`，逐步上调并压测 |
| SSE 拆分引入新复杂度 | 先只做 nginx 层分离，不急着拆服务 |

## 7. 阶段 4：可观测性 + 过载保护（P2-1/P2-2）

### 解决什么问题

当前过载时"能降级但不可见、不可控"：命令积压没有指标和告警，模型网关慢没有熔断。

### 方案

1. **命令队列指标**：在 async worker 暴露 `async_command_queue_depth`（pending/leased 数）、`async_command_throughput`、`async_command_processing_latency` 到 Prometheus。
2. **告警规则**：`deploy/prometheus/rules/` 新增：
   - 队列深度 > 阈值（如 > 200）持续 5 分钟 → 告警；
   - 命令平均延迟 > 模型网关超时 → 告警；
   - DB 连接池使用率 > 80% → 告警。
3. **背压/拒绝策略**：队列过深时，admission 返回 `429 RATE_LIMITED` 或 `503`，而不是继续堆积（保护 worker 与 DB）。
4. **模型网关熔断**：在 `ModelGatewayClient` 加简单的熔断器——连续失败 N 次后短路一段时间，快速失败而不是硬扛 60s×重试。

### 预期收益

- 过载可观测、可告警，运维能在崩溃前介入。
- 熔断 + 背压让系统在模型网关故障时"快速失败"而不是"慢速堆积"。

### 风险与回退

| 风险 | 缓解 |
|---|---|
| 背压误伤正常突发 | 阈值设宽松（如队列 200），灰度观察 |
| 熔断误判导致短暂不可用 | 熔断窗口短（如 30s），半开探测 |

## 8. 阶段 5：稳定性兜底（P1-4/P2-3）

### 解决什么问题

认证每请求回查 DB 的额外开销；Redis 单点单连接的高可用性。

### 方案

1. **token 绑定缓存**：`_bind_principal_to_account` 的结果按 `jti` 缓存 60s（Redis 或进程内 LRU），减少每请求一次 DB 查询。**注意**：缓存会使 `auth_version` 吊销延迟 ≤60s，需在文档中明确"吊销最多 60s 生效"（当前是即时）。
2. **Redis 高可用**：内网规模下先做"连接失败自动重建 + PG advisory lock 兜底"（已具备），后续按需上 Redis Sentinel。
3. **启动快照与 drift 告警**：已具备（阶段 4 加固），纳入常规运维巡检。

### 预期收益

- 认证路径 DB 压力下降，延迟降低。
- Redis 故障时核心业务（会话锁）不中断。

### 风险与回退

| 风险 | 缓解 |
|---|---|
| token 缓存延迟吊销 | 明确"吊销最多 60s 生效"的权衡；若要求即时吊销则不做缓存 |
| Redis Sentinel 增加运维复杂度 | 内网规模先不做，仅文档化升级路径 |

## 9. 阶段间依赖

```
阶段1 (worker并发) ──► 阶段2 (多进程)
        │                   │
        └──► 阶段3 (连接池调优) ◄──┘
                    │
                    ▼
              阶段4 (可观测+背压/熔断)
                    │
                    ▼
              阶段5 (token缓存/Redis高可用)
```

阶段 1 与阶段 2 是吞吐核心，建议合并交付（先并发消费，再加多进程）；阶段 3 需配合阶段 1/2 一起调（连接池不扩，并发 worker 会撞连接池上限）。

## 12. 实施记录（阶段 1）

> 提交：`e9a9af3 perf(async-worker): 阶段1 R7 worker 并发消费`
> 实施时间：2026-08-13

### 12.1 改动内容

| 文件 | 改动 |
|---|---|
| `app/core/config.py` | 新增 `ASYNC_COMMAND_MAX_CONCURRENCY`（默认 8，范围 1~32） |
| `app/agent_runtime/async_command_worker.py` | `run_once()` 从「逐条 `await`」改为「按 session 分组 + 组内串行 + 跨会话 `asyncio.gather` 并发 + 全局 `Semaphore` 约束」 |
| `app/main.py` | lifespan 传入 `max_concurrency` |
| `tests/test_async_command_worker_unit.py` | +4 个并发语义测试 |

核心逻辑：

```python
by_session = {}
for cmd in claimed:
    by_session.setdefault(cmd.session_id, []).append(cmd)
sem = asyncio.Semaphore(max_concurrency)
async def process_group(cmds):
    for cmd in cmds:            # 组内 for = 同会话串行
        async with sem:         # 跨会话受全局上限约束
            outcome = await self._process(cmd)
await asyncio.gather(*(process_group(cs) for cs in by_session.values()))
```

**同会话串行由「分组 + 组内 for」保证**，不依赖业务层锁——因为 review 路径内部没有 SessionLock，此前全靠 worker 串行兜底，这一步不能省。

### 12.2 实测提速（微基准）

用「模拟单次模型调用 200ms 的 fake handler + 20 条命令（默认 batch_size=10 每批认领 10 条）」测量：

| 场景 | 耗时 | 结论 |
|---|---|---|
| 不同会话 `max_concurrency=1`（改造前串行） | 2053ms | 基线 |
| 不同会话 `max_concurrency=8`（改造后并发） | 406ms | **提速 5.1×** |
| 同会话 `max_concurrency=8` | 2042ms | 仍严格串行（符合预期） |

> 说明：该 5.1× 是**并发机制的确定性提速**（batch_size=10、并发 8 → 两轮并发 8+2）。真实吞吐的提速上限由 `max_concurrency`、`batch_size`、模型网关连接池（64）、DB 连接池（30）共同决定，需用真实模型网关压测才能得到端到端数字。

### 13.2 多进程安全基座（为何无需改业务代码）

多 worker 横向扩展的前提是**三个关键机制已在早前设计为多进程安全**：

| 机制 | 多进程安全依据 |
|---|---|
| 命令 worker claim | `SELECT ... FOR UPDATE SKIP LOCKED`（`app/agent_runtime/async_command.py`），两个 worker 同时 claim 拿到不相交命令集 |
| outbox publisher claim | 同样 `FOR UPDATE SKIP LOCKED`（`app/agent_runtime/repository.py`） |
| 会话锁 | PostgreSQL advisory lock 是跨进程唯一权威（`app/services/session_lock.py` R8-A 注释） |

其余进程级单例（`get_settings` / `get_engine` / `get_redis` / 模块级缓存）都是**每进程独立**，无跨进程共享状态。

**为什么只告警不阻断**：连接池超限是容量提示而非配置错误——PG 会在运行时拒绝超限连接，不阻断启动可避免 DB 短暂不可达时误伤启动。

实测：PG `max_connections=100`，默认 `API_WORKERS=4 × (10+20) = 120 > 100` 时启动打印告警；单 worker `30 < 100` 无告警。

**多 worker 部署时的正确姿势**（二选一）：
- 降低每进程池：`API_WORKERS=4 DB_POOL_SIZE=8 DB_POOL_MAX_OVERFLOW=8` → 4×16=64 < 100；
- 或调高 PG `max_connections` ≥ `workers×(pool_size+max_overflow)` + 运维余量。

### 14.2 背压 / 拒绝策略

- 阈值 `ASYNC_COMMAND_MAX_QUEUE_DEPTH` 默认 200，`0` 禁用。
- admission 在「未终结命令数（queued+running）≥ 阈值」时返回 `503 QUEUE_OVERLOADED`（`Retry-After` + `retryable: true`），**不 fallback 同步路径**——同步同样会堆积，只会把压力从 worker 转移到请求线程。
- `count_active()` 查询失败时**宁可放行**也不拒绝临床请求（监控查询失败不应阻断业务）。

### 14.3 模型网关熔断器

- `CircuitBreaker` 三态：闭合 →（连续失败 ≥ 阈值）→ 打开 →（冷却结束）→ 半开探测 →（成功闭合 / 失败重开）。
- 只在 `_request_with_retry` 层面计数：**一次逻辑调用即使传输层重试 3 次失败也只计 1 次熔断失败**。
- 只把「可重试故障」（超时/连接失败/5xx/429）计入熔断；客户端 4xx（非重试）是调用方 payload 问题，不触发熔断。
- 打开期间请求快速失败（不进入 60s×重试慢路径），避免模型网关持续故障时放大延迟与积压。
